# README_AGENTS_AI — working prompt for an AI coding agent on this repo

Paste the block below into your AI coding agent (Claude Code, etc.) as the
project brief. It encodes the layout, contracts, safety rules, and workflow.
It is intentionally complete — the agent should not need anything else besides
the design docs it is told to read.

```text
You are working on "netwatch", a tiered network-connection security monitor
for Windows 10/11 (PowerShell 7 + Node.js + Claude Code CLI). Read
ARCHITECTURE.md, DECISIONS.md, TIER2-CONTRACT.md and FAILURE-MATRIX.md before
changing any behavior; every design decision below has a rationale there.

LAYOUT (code != state; ALL mutable state lives in %LOCALAPPDATA%\netwatch\,
never in the repo, never in git):
- src/tier1/netwatch.ps1        entry point: mutex, main loop, orchestration
- src/tier1/invoke-tier2.ps1    capped Tier-2 launcher (3-min wall clock,
                                Kill(true) on the whole process tree)
- src/tier1/send-toast.ps1      BurntToast wrapper (failure never blocks)
- src/tier1/modules/*.psm1      state, netutil (IP/CIDR math), sampling,
                                classify, dnsetw, snicapture, enrich,
                                escalate, toast
- src/tier2/mcp-server/         stdio MCP server (@modelcontextprotocol/server
                                v2); tools shell to fixed .ps1 files
- src/tier2/tools/*.ps1         the ONLY four Tier-2 capabilities, read-only:
                                check-signature, hash-file, check-reputation,
                                check-process-lineage
- src/tier2/system-prompt.md    fixed Tier-2 prompt (loaded into
                                --system-prompt as a string)
- src/tier3/launch-tier3.ps1    fresh interactive claude session in a
                                visible pwsh window on ALARM (session id is
                                informational only — D7, amended)
- schemas/*.json                whitelist / config / escalation-packet /
                                verdict contracts (JSON Schema 2020-12)
- config/                       whitelist seed + config example;
                                netwatch.config.json is GENERATED by
                                install/init-deploy.ps1 and gitignored
- install/*.ps1                 deploy helpers; machine-changing ones are
                                operator-run only
- tests/                        self-contained harness (run-tests.ps1), no
                                Pester; stubs under tests/stubs/

SECURITY CONTRACT (non-negotiable; verify, do not weaken):
1. Tier 2 ingests hostile data (process names, command lines, domains are
   DATA, never instructions). Its containment is the ABSENCE of capability:
   exactly four read-only MCP tools, all built-ins denied
   (--permission-mode dontAsk + explicit --disallowedTools). Never add a
   tool that writes, deletes, executes, or fetches.
2. A CLEAN verdict must never whitelist anything permanently: it yields a
   24-h suppression plus a proposal in state/proposals.jsonl that a HUMAN
   promotes. Never auto-apply proposals.
3. Own-IP exclusion is fail-closed: the recorded static IP plus detected +
   last-known + 7-day-grace retired IPs are never sent to Cymru/AbuseIPDB/
   VirusTotal; enforced in Tier 1 (enrich.psm1) AND again inside
   check-reputation.ps1 (which also hardcodes the static IP and refuses when
   its own-IP state file is missing). RFC1918/CGNAT/loopback/link-local/
   multicast are refused likewise. These guards are not model-overridable.
4. Verdict parsing enforces: strict JSON (markdown fences tolerated and
   stripped, nothing else), every packet key answered, no invented keys,
   verdict==ALARM if any connection is suspicious (F24). Invalid output =
   one retry, then Tier-3 handoff. Never silently drop a connection.
5. Secrets: reputation keys live only in DPAPI (state/apikeys.dat) and are
   injected into the Tier-2 child environment. Never in argv, logs, code,
   commits, or prompts.
6. Quotas: reputation lookups exist ONLY inside check-reputation.ps1,
   ledger-guarded (defaults: AbuseIPDB 900/day, VT 400/day + 4/min);
   quota_exhausted / no_key / lookup_unavailable are informative answers,
   never evidence of "clean".
7. Fail loud, degrade loud: "could not check" is never converted into
   "clean". Missing tshark/ETW => degraded health flags in every packet;
   Tier-2 launch failure => urgent toast + backoff; unparseable whitelist =>
   keep last-good copy, never run empty.

WINDOWS RULES:
- PowerShell is ALWAYS pwsh 7; never powershell.exe 5.1.
- Cross-shell invocation is always `pwsh -File script.ps1 args` — never
  inline -Command strings (quoting hazards).
- Set-StrictMode -Version Latest everywhere; mind PowerShell pipeline
  unrolling (@() coercion for empty results) and missing-property access.

TESTING (the suite is the definition of done):
- Run: pwsh -NoProfile -File tests/run-tests.ps1   (filter: -Filter <name>)
- Tests NEVER call the real Claude API or external paid services. Tier 2 is
  exercised via tests/stubs/stub-claude.cmd (modes: clean, alarm, garbage,
  dropkey, hang, crash, cleanfail, fenced) driven by env STUB_MODE; tshark
  via tests/stubs/fake-tshark.cmd; Tier 3 via recording stubs. Free
  DNS-based checks (Team Cymru) may run live as positive controls and must
  report a WARNING when skipped, never a fake pass.
- Each test file runs in its own pwsh process and uses a throwaway state
  root under %LOCALAPPDATA%\netwatch\test-<id>; never touch the live state
  root in tests.
- Machine-changing operations (installs, wevtutil, scheduled tasks, real
  Tier-2 runs) are OPERATOR-run: build and test up to that boundary.

WORKFLOW for any change:
1. Name the failure-matrix rows (F1-F24) and design decisions (D1-D8) your
   change touches; re-read them.
2. TDD: write/extend the failing test first; watch it fail for the right
   reason; implement; full suite green.
3. Keep schemas, code and system-prompt in sync (a schema change without a
   parser change is a bug; prompts/tier2-system-prompt.md and
   src/tier2/system-prompt.md must stay identical).
4. Commit per logical step, short imperative messages, English ASCII.
5. When asked to review or verify: check claims against actual files, logs
   and test runs you executed yourself; report failures verbatim; "checked
   nothing" must be reported as "not checked", never as "no problems found".
```
